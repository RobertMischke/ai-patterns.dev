Proposed decision

Format first

A durable editorial record, not another research summary

The repository already keeps research-stage files such as research/critique.json and research/counter-arguments.json. Those synthesize source material while a pattern is authored. The proposed top-level critique.json has a different job: it is the long-lived discussion and resolution record after publication. Migration should curate research points into durable entries, never copy them wholesale.

Locality

One companion

data/patterns/<slug>/critique.json travels with pattern.json. A build scans companions and derives all indexes.

Identity

Stable entries

Every entry gets a repository-wide PC-nnnn ID. Anchors may drift; IDs, history, and links remain stable.

Freshness

Revision-bound

The companion records the pattern fingerprint; each rating says which fingerprint it assessed and when to review it.

Status semantics

  • Open: material and unresolved; not necessarily correct.
  • Addressed: the pattern now answers or bounds it without adopting its proposal.
  • Absorbed: the critique changed the pattern; preserve the entry as provenance.
  • Rejected: an accountable editor declined it with reasons. Rejected does not mean disproven.

Rating model

Three questions, three words, no arithmetic

A rating is triage, not truth. The recommended model asks whether the critique is about the pattern, whether its reasoning holds up, and what delay costs. These axes must never be summed or averaged: direct + weak + blocking conveys a very different editorial situation from direct + compelling + later.

Relevance

Does it bear on the claim?

Adjacent · useful context
Material · changes application or boundary
Direct · attacks or extends the central claim

Strength

How well is it supported?

Weak · assertion or poor fit
Plausible · coherent with some grounding
Compelling · strong evidence and reasoning

Urgency

When must it affect revision?

Later · backlog safely
Next revision · resolve before material expansion
Blocking · publication or use risks misleading readers

Who may rate?

Canonical rating: the named pattern author or an accountable editor. They own the disposition and can explain it in review.

Readers: submit their own triplets and reasons as advisory assessments. The interface may summarize distributions, but a crowd average must not overwrite the canonical rating.

LLM judges: advisory only, always labeled with run provenance. Models may challenge ratings or surface disagreement; they may not close an entry or determine its public priority.

How ratings age

  • Mark a rating stale immediately when validAgainst no longer matches the pattern fingerprint.
  • Review blocking ratings within 30 days, next-revision ratings within 90 days, and later ratings within 180 days.
  • A terminal status does not erase the rating; it records the pressure that shaped the decision.
  • Re-rating updates the assessment fields in git history. It does not rewrite the original claim or resolution.

Edit-mode UX

The argument stays beside the sentence it challenges

Desktop uses a synchronized split view: pattern fields on the left, filtered critique on the right, with a thin anchor rail connecting both. Narrow screens switch to margin-note markers that open a critique drawer. The default reader view remains calm; edit mode is deliberate and local.

Core interactions

  • Filter by type, status, any rating axis, staleness, and target pattern.
  • Select text or focus a JSON field to add an anchored entry inline.
  • Require grounding before saving; allow an explicit “observation” when no publication exists.
  • Show rating labels in full. Color supports type and status but never carries meaning alone.
  • Preview anchor drift and pattern fingerprint changes before writing.

Absorb without erasing

“Absorb into text” opens a revision preview rather than changing status immediately. Saving writes the pattern revision, updates the fingerprint, stores a resolution.revisionRef, and only then changes the critique to absorbed.

If a save fails validation, both files remain unchanged. The critique never disappears from the public history; it becomes evidence for why the pattern reads as it does.

Revision loop

NoticeReader, editor, or model proposes a grounded entry.
TriageEditor anchors, types, rates, and deduplicates it.
ReviseAuthor answers, absorbs, or rejects with a rationale.
ValidateSchema, links, anchors, fingerprint, and site build pass.
RememberResolution remains visible and later changes may reopen it.

This deliberately mirrors the platform’s dossier lifecycle as prior art: investigation remains visible while a dossier becomes decision-ready, and a decision changes its disposition rather than deleting the branches that informed it. Pattern critique applies that living-document discipline at entry scale.

Beyond the brief

Turn critique into evidence infrastructure

LLM-seeded critique rounds

Run bounded, role-diverse rounds—skeptical practitioner, evidence auditor, boundary-case finder, and adjacent-pattern mapper. Store candidates as origin.kind: llm-seed with run provenance in a staging view. A human editor must deduplicate, verify grounding, and accept a candidate before it enters the companion.

Model and thinking-level selection belongs to the repository’s routing policy. The format must not hard-code a provider, model, or cost-based downgrade, and an LLM judge remains advisory even when several models agree.

Cross-pattern argument reuse

An entry’s targets[] can name several patterns. The canonical entry lives in one companion; builds include it on every targeted pattern and report missing backlinks. If reuse becomes common, add a derived argument index—not a second editable registry.

The example’s portability counter-argument targets both sidecar-metadata and companion-app.

Public contribution without public writes

Start with a structured issue form (type, target, claim, grounding). A maintainer or bot converts accepted proposals into schema-valid changes. A later site form may create the same issue through a narrowly scoped service. This is PR-less for the contributor but still produces a reviewed git change.

Credibility through visible disagreement

Publish open, rejected, and absorbed critique alongside sources and revision history. Coverage metrics should report grounded open questions, stale ratings, and resolved critique—not a leaderboard. A register that shows its strongest objections and how they changed the text is more credible than one that only accumulates supporting citations.

Recommended path

Static read path first; small local editor second; expose that editor through the existing development workflow only after its file operations and validation are reliable.

This sequence preserves one source of truth at every step. The editor is a view and writer over repository files, never an independent discussion database.

Delivery slices after approval

Four independently reviewable increments

Format + validationAccept the schema location and ID allocator; validate type, grounding, terminal resolutions, targets, fingerprints, and dates.
Static readerRender critique on pattern pages with accessible filters, stable anchors, stale markers, and cross-pattern backlinks.

Contribution + seedsAdd the structured issue path and curated LLM rounds; measure acceptance, duplication, aging, and revision impact.

Acceptance gates per slice

  • Malformed companions and broken target patterns fail deterministically.
  • No critique entry can be published without grounding and a complete canonical rating.
  • Status changes to addressed, absorbed, or rejected require a resolution.
  • Fingerprint mismatch is visible in builds and the UI; it is never silently refreshed.
  • The public page works without JavaScript; filters enhance rather than gate access.
  • Keyboard and screen-reader users can move between anchors and entries.
  • Absorption is atomic and preserves the critique entry plus revision reference.
  • Reader or LLM signals cannot alter status or canonical rating without human review.
